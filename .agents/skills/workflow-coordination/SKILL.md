# Workflow coordination

This skill exists to coordinate consequential **multi-workflow engineering execution** when ownership, dependencies, or independent verification must cross stages. It is a procedural contract, **not** a scheduler, permission grant, lock service, or substitute for repository instructions.

1. **Reconcile actual state.** Read applicable `AGENTS.md` instructions and current repository evidence; inspect Git status/diff, existing decisions, partial work, and active plan. Preserve user changes. Do not restart completed work from a stale handoff. If the request is actually a single specialist workflow, route there and stop coordinating.
2. **Declare the coordination boundary.** State the observable outcome, non-goals, affected paths/interfaces, authorization limits, risk tier, task identifier, and starting revision. Identify the minimal dependency graph with named deliverables and acceptance gates. Consult `references/coordination-contract.md` for risk, routing, gates and handoff rules.
3. **Select capabilities that exist.** Assign the minimum distinct specialist roles needed. Use available named skills/agents only after confirming discovery; a descriptive role is not proof of a configured agent. Parallelize bounded **read-only, independent** investigation where tooling and isolation allow it. One writer owns any overlapping file set at a time; a prompt alone does not enforce a lock. Serialize conflicting work and integrations.
4. **Gate every handoff.** Each stage must identify its input revision, scoped owner, artifact or diff, actual observations, required checks and dispositions. Use the existing project ledger when authoritative; otherwise use `references/handoff-schema.md`. For structured records, optionally run `scripts/check_handoff.py` on the saved JSON record. A successful lint does **not** prove an agent's claims or external authorization.
5. **Integrate and verify.** Before reusing evidence, compare the stage's input and output revision/dirty-tree state to the current repository. Reconcile competing edits and stale results. Run focused tests first; broaden to integration, regression, security, performance, documentation or independent review only where the affected contracts and risk warrant. L2/L3 changes require independent diff/evidence review when available; if unavailable, report reduced assurance rather than impersonating independence.
6. **Repair with bounded retries.** Record each material finding, owner, revision, fix and invalidated checks. Re-run affected verification and review the fresh diff. Apply the repository's retry/review policy, otherwise cap total review passes at three. An exhausted cap, uncertain ownership, denied approval, or unknown external-write outcome requires an explicit safe stop, not an escalation loop.
7. **End on observable evidence.** Mark `COMPLETE` only when the current revision meets its applicable acceptance criteria, all required gates were actually run and passed, and no material unresolved findings remain. Otherwise report `PARTIAL`, `BLOCKED`, `FAILED` or `CANCELLED` with specific evidence, missing checks and next authorized action. Never infer success from delegation or a handoff message.

**Action boundary:** Source edits are not authorization to commit, push, open PRs, merge, deploy, alter production data, or publish. Independently confirm scope and permission for each external or consequential operation; obey higher-priority repository rules.

**Output:** concise coordination handoff with task/baseline/current revision, selected workflows and owners, changed paths, checks with actual results, independent review disposition, material risks, and terminal state. For failed/blocked/inconclusive branches use `references/coordination-contract.md` before proceeding.
